# Hot-path perf baseline (rust-core 1.3)

Black-box latency of the hot path, measured the way the user pays for it:
one process per hook invocation, spawned as the shims spawn it, wall clock
from spawn to exit. The runner drives an implementation binary (the built
TypeScript CLI by default, `SOFAR_CONFORMANCE_BIN` for a candidate) so the
TypeScript numbers recorded here are the target a native core is measured
against with the same code.

```
npm run perf                                             # measure the TypeScript reference (~6 min)
SOFAR_PERF=1 SOFAR_PERF_RECORD=1 npx vitest run --project perf        # re-record baseline.typescript.json
SOFAR_PERF=1 SOFAR_CONFORMANCE_BIN=target/release/sofar-core npx vitest run --project perf   # a candidate, with ratios vs the target
SOFAR_PERF=1 SOFAR_PERF_GATE=1 SOFAR_CONFORMANCE_BIN=… npx vitest run --project perf         # the 3.3 gate: every p50 and p95 ≤ target
SOFAR_PERF_CELLS=i10-1mb,repo,floor …                    # a subset (with RECORD: merged into the baseline)
SOFAR_PERF_ITER=50 …                                     # spawns per measurement (default 20)
```

Results land in `baseline.typescript.json` (+ `.md`) when recording, else in
the OS temp dir as `sofar-perf.<implementation>.json` / `.md`.

## Cells

Six scale cells generated by `scale.ts` from the synthetic builders' fixed
clock (same bytes every run, never checked in): 10 / 100 / 1,000 initiatives
in the `.sofar/`, crossed with a bound log of 1 MB (3,595 events) and 10 MB
(35,903 events) shaped like a real initiative log — plan, ten decisions
(five guarded), sessions of 24 mechanical events each with a write-back,
every tenth sibling leaving a session open on a path the bound record also
edits. Plus `repo`, this repository's own record (the 1.2 fixture, 55
initiatives, 7.6 MB) on `main`, bound to session-driver (0.6 MB), and
`floor`, a root with no record at all.

Every cell is a real git repository with one commit (the shipping notice
and identity read what a developer's clone has), a scratch HOME and the
conformance harness's pinned environment.

## Measurements

Per cell, `iterations` sequential spawns each; p50 and p95 by nearest rank,
plus the minimum:

| measurement | what it exercises |
| --- | --- |
| session-start (index warm) | fold + digest render + registration scan, index present |
| session-start (index cold) | the same with `.sofar/.index/` deleted before every spawn |
| post-tool Edit | append + projections + guard read, registered open session |
| user-prompt (nudge) | drift ≥5 → the nudge path folds and renders |
| stop (blocked) | debt computation + block (exit 2) |
| session-end | closes a pre-registered session: fold + append + projections |
| statusline | the status-bar render (styled) |
| status <slug> | the full CLI (commander bundle) plain render — not a hook, kept for 2.4 |
| floor / session-start (no record) | boot + stdin parse + unbound notice: what a native core removes |

The header also carries the bare `node -e 0` spawn time. For the TypeScript
reference only, an in-process section times `foldLog` and `renderStatus`
directly, separating the engine's own work from node's boot.

Sessions the matrix needs (an open session five edits past any write-back,
one closable session per iteration) are registered through the binary
itself, so a cell is prepared the same way for any implementation.

## Reading the baseline

The recorded machine is in the JSON header (`machine`, `commit`,
`recordedAt`); numbers from a different machine are not comparable. The gate
(`SOFAR_PERF_GATE=1`) is meant to run candidate and reference on the SAME
machine in the same sitting: re-record the reference first, then measure the
candidate.
